# 🤝 NOVA AI TRPG — Регламент взаємодії чатів та правила розробки (Workflow Rules)

Цей документ є **законом розробки** для всіх чатів проєкту (`Architect`, `Backend`, `Client`).  
Він гарантує узгодженість архітектури, безпеку кодової бази та відсутність несподіваних поломок.

---

## 1. Ролі чатів та ієрархія
1. **Головний Архітектор / Оркестратор (Головний чат):**
   - Володіє загальною картиною всієї системи.
   - Затверджує будь-які зміни в `docs/API_CONTRACT.md`.
   - Єдиний формує та затверджує нові задачі для дорожніх карт разом із Ванею.
   - Проводить рев'ю рішень суміжних чатів та координує спільні релізи.
2. **Backend Чат (Python / FastAPI):**
   - Відповідає **ВИКЛЮЧНО** за директорію `Backend_Python/`.
   - Заборонено чіпати C# код або пропонувати переключатися на клієнт.
   - Бере завдання **ВИКЛЮЧНО** з `docs/BACKEND_ANALYSIS.md`.
   - Суворо дотримується структури DTO з `docs/API_CONTRACT.md`.
3. **Client Чат (C# / Avalonia UI / .NET 10):**
   - Відповідає **ВИКЛЮЧНО** за директорію `NovaTrpgClient/`.
   - Заборонено чіпати Python код або пропонувати переключатися на бекенд.
   - Бере завдання **ВИКЛЮЧНО** з `docs/CLIENT_ANALYSIS.md`.
   - Суворо мапить DTO з `docs/API_CONTRACT.md`.

---

## 2. Файли завдань та заборона самовільних дій
- `docs/BACKEND_ANALYSIS.md` та `docs/CLIENT_ANALYSIS.md` — це персональні дорожні карти чатів.
- Чатам **СУВОРО ЗАБОРОНЕНО** вигадувати нові завдання поза цими файлами.
- **Вихід за межі завдань:** Якщо чат вважає, що потрібні додаткові кроки, фічі чи зміни — він не робить їх самовільно, а пише Вані:
  > *«Ця дія виходить за межі поточної дорожньої карти. Потрібно повідомити Архітектора для узгодження завдання з Ванею.»*

## 3. «Золоті правила» Git & Безпеки (Критично важливо!)
- 🛑 **СУВОРА ЗАБОРОНА НЕАВТОРИЗОВАНИХ КОМІТІВ/ПУШІВ:**  
  Жоден чат (і навіть Архітектор!) **НЕ МАЄ ПРАВА** виконувати `git commit`, `git push` або створювати Pull Request без прямого дозволу та підтвердження від Вані!  
  *Процедура:* Чат готує зміни -> показує `git status` і diff -> запитує: *"Ваня, зміни готові, чи можу я зробити коміт з описом '...'?"* -> чекає підтвердження.
- 🌿 **Єдина робоча гілка `dev` (Монорепозиторій):**  
  Обидва чати ведуть розробку в єдиній спільній гілці `dev`.
  Оскільки Backend пише виключно в `Backend_Python/`, а Client — виключно в `NovaTrpgClient/`, файли не конфліктують, а зміни та документація завжди доступні обом сторонам одночасно на диску.
  - Кожен чат додає до коміту **тільки свої файли** (наприклад, `git add Backend_Python/` або `git add NovaTrpgClient/`).
  - Ніхто не комітить напряму в `main`! Злиття `dev -> main` здійснюється тільки після узгодження Архітектором.
- 🔒 **Безпека ключів:**  
  У репозиторій ніколи не додаються файли з реальними API-ключами або токенами. Усі секрети читаються з `.env`, який обов'язково є в `.gitignore`.

## 4. Правило міжсервісних змін (Cross-Service Boundary)
- **Якщо чат Backend** змінює або планує змінити:
  - Маршрут URL (ендпоінт);
  - Назву, тип або вкладеність будь-якого поля в JSON (`raw_text`, `intents`, `player_state`, `story`);
  - Статуси відповідей чи логіку генерації;  
  👉 **Він ЗОБОВ'ЯЗАНИЙ** скласти повідомлення:  
  *«Ваня, передай чату Client: змінено схему DTO [опис]»*.

- **Якщо чат Client** потребує нового поля чи іншого формату даних:  
  👉 **Він НЕ вигадує власні поля самостійно**, а формує запит:  
  *«Ваня, передай чату Backend: для нового віджета потрібне поле [назва] в DTO. Потрібно узгодити через docs/API_CONTRACT.md»*.

---

## 5. Непорушне правило геймплейного пайплайну
Модуль **Аналізатора стану (State Analyzer)** працює **СТРОГО ПОСЛІДОВНО** після завершення відповіді Оповідача:
$$\text{Гравець} \longrightarrow \text{Оповідач (GM)} \longrightarrow \text{Аналізатор} \longrightarrow \text{Оновлення стану}$$
- Аналізатор оцінює не лише намір гравця, а й те, **що саме відбулося в описі Оповідача**.
- Паралелити Оповідача та Аналізатора суворо заборонено!
